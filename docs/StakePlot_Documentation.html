1. Executive Summary

StakePlot is a full-stack fintech mobile application that enables Indian users to aggregate their bank accounts, credit cards, and financial data in one place via the Finvu Account Aggregator (RBI-approved open banking framework).

Core Capabilities

  • Bank account linking via Finvu AA
  • Automated transaction sync & categorization
  • Credit card statement scraping from Gmail
  • Recurring payment & auto-pay detection
  • Personal and shared collections with expense splitting
  • Budgeting, analytics & financial calculators
  • Community social features

Architecture Highlights

  • Flutter cross-platform mobile app
  • Node.js/TypeScript microservices
  • MongoDB (document store)
  • Redis (cache + pub-sub)
  • Bull queue (async jobs)
  • AWS (S3, KMS, Secrets Manager)

Key Integration Partners

Finvu: RBI-approved Account Aggregator for open banking. Handles consent, bank discovery, and encrypted FI data delivery.

Gmail API (Google OAuth 2.0): Scrapes credit card statements directly from user's inbox with permission.

Firebase: Authentication, crash reporting (Crashlytics), and push messaging (FCM).

OneSignal: Cross-platform push notification delivery.

4.1 Hive Local Storage

Hive is used as the offline-first local database in Flutter. It provides encrypted key-value boxes that persist data between app sessions.

Why Hive?

Hive offers native Dart performance (no platform channels), AES-256 encryption support, and works seamlessly with GetX reactive state. It is used to cache user tokens, bank account info, and fetched transactions so the app loads instantly even without internet.

HTTP Service Layer (backed_connections/)

All API calls go through a centralized HTTP service that automatically attaches JWT headers from Hive storage:

class ApiService {
  static Future<dynamic> post(String url, Map body) async {
    final token = Hive.box('userBox').get('jwt_token');
    final response = await http.post(
      Uri.parse(url),
      headers: {
        'Content-Type': 'application/json',
        'Authorization': 'Bearer $token',
      },
      body: jsonEncode(body),
    );
    return jsonDecode(response.body);
  }
}

5. Finvu Integration Documentation

What is Finvu?

Finvu is an RBI-licensed Account Aggregator (AA) that enables users to share their financial data from banks with applications in a secure, consent-based manner. StakePlot uses Finvu to link bank accounts and fetch transaction history without storing raw banking credentials.

Regulatory: Compliant with RBI's Account Aggregator Framework (2021)
Data Security: All financial data is end-to-end encrypted between the bank (FIP) and the application (FIU)

High-Level Architecture

5.1 Finvu API Endpoint Reference

Base path: /api/v1/bank/finvu — All endpoints require JWT Auth

POST

/finvu/login

Controller: finvu-controller.ts → loginAndGetHandleId()

Purpose: Initiates a consent request with Finvu for a user. Returns a consentHandleId that the Flutter Finvu SDK uses to start the consent flow (OTP, account discovery, linking).

Request Body
FieldTypeDescription
custIdstring requiredCustomer ID in Finvu format (e.g., user@finvu)
numberstring required10-digit mobile number of the user
Response (200 OK)
FieldTypeDescription
successbooleantrue
consentHandleIdstringHandle ID to pass to Finvu SDK; stored in MongoDB with 24h TTL
Error Responses
StatusMeaning
400Invalid custId or number format
502Finvu API unreachable

Sequence of Operations

  1. Validate request body (Joi schema)
  2. Call Finvu API: POST /v2/consent/request with consent template payload
  3. Receive consentHandle from Finvu
  4. Store in ConsentHandleId collection with userId, 24h TTL
  5. Return consentHandleId to Flutter app
// Success response example

  "consentHandleId": "fcd8e93a-1234-4abc-8765-abcdef012345"
}
POST

/finvu/fetchData

Controller: finvu-controller.ts → fetchTransactions()

Purpose: Main data fetch endpoint. Polls consent status, gets consent details (date range), initiates FI request, and enqueues an async Bull job to fetch and decrypt transactions.

FieldTypeDescription
handleIdstring requiredConsent handle ID returned from /login
custIdstring requiredUser's Finvu customer ID
Response (200 OK)
FieldTypeDescription
successbooleantrue
sessionIdstringFI session ID for tracking job
messagestringStatus message

Sequence of Operations

  1. Call fetchConsentStatus(handleId) — poll up to 2 times (5s gap)
  2. Extract consentId from status response
  3. Call fetchConsentDetails(consentId) — get allowed date range
  4. Call Finvu: POST /v2/FI/request — get sessionId
  5. Cache sessionId in Redis (TTL: 600s)
  6. Store in Finvu model (MongoDB, 24h TTL)
  7. Staging: Enqueue Bull job fetch-transactions
  8. Production: Wait for Finvu webhook notification
  9. Return sessionId to client
POST

/finvu/fetchWeekly

Controller: finvu-controller.ts → fetchTransactionsWeekly()

Purpose: Lightweight weekly sync for already-linked bank accounts. Reuses existing consent to fetch the last 7 days of transactions without requiring user interaction.

Auth: Service-to-service call (can be triggered by cron or user). Uses existing Bank model records to re-initiate FI request without new consent.

6.2 Transaction Processing Flow

flowchart TD A[Finvu Encrypted Data] --> B[Decrypt with DEK / AWS KMS] B --> C[Parse raw FI schema XML/JSON] C --> D[Normalize to Transaction model] D --> E{Duplicate check} E -->|Duplicate| F[Skip / Update count] E -->|New| G[Narration parsing] G --> H[Extract: merchant name, VPA, bank handle] H --> I[AI Categorization service] I --> J[Assign category + subcategory] J --> K[Store in MongoDB] K --> L[Recurring payment detection] L --> M{Is recurring?} M -->|Yes| N[Create/update RecurringPayment record] M -->|No| O[Mark needsReview if uncertain] N --> P[Update analytics aggregates] O --> P P --> Q[WebSocket notify client] Q --> R[Flutter displays transactions]

6.3 Transaction Logic Details

Categorization Logic

  • ML model analyzes narration + name fields
  • Keywords matched against category taxonomy
  • Examples: "SWIGGY" → Food & Dining / Food Delivery
  • Examples: "NETFLIX" → Entertainment / Streaming
  • Low-confidence predictions set needsReview: true
  • User corrections feed back into model

Deduplication Logic

  • Compound check: txnId + transactionTimestamp + amount
  • If exact match exists → skip insertion
  • Soft dedup: near-identical narrations within 1min window flagged
  • Manual transactions never deduped

Recurring Payment Detection

  • Groups transactions by counterpartyName or merchant
  • Checks for consistent amount ± 5% tolerance
  • Checks for regular time intervals (7/14/30/365 days)
  • High-confidence recurring → auto creates RecurringPayment
  • Assigns expectedFrequency: weekly/monthly/yearly

Transaction Grouping

  • Similar transactions clustered by merchant + category
  • User can bulk-categorize an entire group
  • Groups visible in analytics view
  • grouped/:groupId/categorize updates all in group

7. Collections Module Documentation

Base path: /api/v1/bank/collections - All endpoints require JWT Auth

Module Overview

The Collections module lets users create personal or shared spending buckets from their existing bank transactions. Personal collections group selected transactions for tracking, while shared collections add members, split expenses equally or manually, track who paid, calculate balances, and record partial or complete settlements.

Frontend Ownership

  • mobile-frontend/lib/Home_Screen/history/collections/ contains the collection home, list, settings, invitations, personal collection, group collection, creation pages, and shared trip/dashboard screens.
  • mobile-frontend/lib/controllers/collections_controller.dart owns GetX state, API calls, Hive cache hydration, socket updates, split actions, balances, invitations, and member limits.
  • mobile-frontend/lib/routes/route_collections.dart centralizes all mobile collection API URLs.
  • mobile-frontend/lib/Hive_localstorage/apisCall/collections_apis.dart persists collection list, details, splits, balances, and limit summary locally.

Backend Ownership

  • mobile-backend/bank-service/src/routes/collection-routes.ts registers protected Express routes for collections, invitations, members, transactions, splits, payments, and balances.
  • mobile-backend/bank-service/src/controllers/collection-controller.ts extracts authenticated user context, validates simple request requirements, calls services, formats success responses, and publishes socket events.
  • mobile-backend/bank-service/src/services/collection-service.ts contains core business rules for collection limits, membership permissions, transaction attachment, split generation, payment records, balances, member limits, close/delete/exit, and transaction-safe writes.
  • collection-invitation-service.ts manages invitation lifecycle for pending, accept, reject, cancel, and collection-level invitation views.

Sequence of Operations

Permission & Limit Rules

Permissions

  • Every collection route uses protect, so req.user._id comes from a verified JWT.
  • Only collection members can fetch details, splits, balances, and collection transactions.
  • CONTRIBUTE members can add transactions, update splits, add/invite members, and update collection details.
  • Only the owner can delete, close, and bulk-set member limits.
  • Members can exit a collection by deleting only their membership.

Limit & Balance Logic

  • User collection limits come from UserConfigService.getUserCollectionLimit().
  • Active collection usage is counted through CollectionMember joined with ACTIVE Collection rows.
  • Available transactions exclude already-attached CollectionTransaction documents.
  • Balances are calculated from Split minus aggregated SplitPayment records.
  • Settlement statuses are PENDING, PARTIAL, or SETTLED.

9.2 Authentication Mechanisms

JWT Flow

  1. User authenticates via Firebase Auth (mobile app) → gets Firebase ID token
  2. Flutter sends Firebase ID token to Main Backend
  3. Main Backend verifies with Firebase Admin SDK → issues its own JWT (signed with JWT_SECRET)
  4. JWT payload: {userId, email, aud: 'bank-service'}
  5. All subsequent requests include: Authorization: Bearer <jwt>
  6. Bank Service verifies JWT with SERVICE_JWT_SECRET, checks aud === 'bank-service'
// auth-middleware.ts (simplified)
export const protect = async (req, res, next) => {
  const token = req.headers.authorization?.split(' ')[1];
  if (!token) return res.status(401).json({ error: 'No token' });

  const decoded = jwt.verify(token, process.env.SERVICE_JWT_SECRET!, {
    audience: 'bank-service'
  });
  req.user = { _id: decoded.userId };
  Sentry.setUser({ id: decoded.userId });
  next();
};

14. Security Considerations

Data Encryption

  • Bank data: Field-level encryption with per-user DEKs
  • DEKs encrypted with AWS KMS CMK (envelope encryption)
  • Gmail OAuth tokens: stored encrypted in MongoDB
  • PDF passwords: encrypted at rest
  • All transit: HTTPS/TLS 1.3

Authentication

  • Firebase Auth for user identity (OAuth 2.0, email/password)
  • Service-specific JWTs with audience restriction (aud)
  • Short-lived tokens (configurable expiry)
  • Refresh token rotation via Firebase

API Security

  • Helmet.js: CSP, HSTS, X-Frame-Options
  • HPP: Parameter pollution prevention
  • Rate limiting: 200 req/15min per IP (global)
  • Joi validation on all request bodies
  • CORS: Whitelist-only origins

Compliance

  • Finvu: RBI Account Aggregator Framework compliant
  • User consent required before any data access
  • Consent TTL enforced (5 days max)
  • Data minimization: only requested FI types fetched
  • Sentry: No PII in error reports

Key Operational Notes

  • Staging vs Production: In non-production, transaction data fetching uses Bull job polling instead of Finvu webhooks. Webhook endpoints must be registered with Finvu for production.
  • Redis dependency: Bank Service requires Redis to be running. Without Redis, consent sessions and pub-sub events will fail.
  • AWS KMS: All bank data decryption requires AWS KMS availability. DEKs cannot be decrypted locally without KMS access.
  • MongoDB TTL indexes: ConsentHandleId (5 days) and FinvuSession (24h) are auto-cleaned by MongoDB TTL. Ensure TTL is enabled on Atlas cluster.
